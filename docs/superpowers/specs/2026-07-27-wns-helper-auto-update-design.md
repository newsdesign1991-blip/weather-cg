# WNS Helper 자동 업데이트 설계

## 목표

사용자가 매 배포 때 `WNS_STOP`과 `WNS_START`를 직접 실행하지 않아도 실행 중인 WNS Helper가 R 드라이브의 최신 배포본을 감지하여 안전하게 교체하고 다시 실행한다.

현재 배포되어 있는 구버전에는 자동 업데이트 코드가 없으므로 이 기능이 포함된 첫 버전으로 넘어갈 때만 한 차례 수동 재실행이 필요하다.

## 선택한 방식

헬퍼 내부의 백그라운드 감시 스레드가 5분마다 다음 두 파일을 비교한다.

- 실행 중인 로컬 `%LOCALAPPDATA%\WNS_Helper\WNS_Helper.exe`
- 기준 배포본 `R:\[F]_Util\WNS\WNS_Helper.exe`

파일 크기와 수정 시각이 다를 때만 SHA-256을 계산한다. 해시까지 다르면 업데이트 대상으로 판단한다. R 드라이브가 없거나 파일을 읽지 못하면 현재 헬퍼를 그대로 유지하고 다음 주기에 재시도한다.

## 안전한 교체 흐름

1. 업데이트 감지 시 새 EXE를 로컬 임시 파일로 먼저 복사한다.
2. 임시 파일의 SHA-256이 R 배포본과 같은지 확인한다.
3. 헬퍼가 처리 중인 HTTP 요청이 없을 때 업데이트 전용 PowerShell 프로세스를 실행한다.
4. 업데이터는 현재 헬퍼 프로세스가 끝날 때까지 기다린다.
5. 기존 로컬 EXE를 `.bak`으로 보관하고 검증된 임시 EXE로 교체한다.
6. 새 EXE를 창 없이 실행한다.
7. 교체에 실패하면 `.bak`을 복원하고 기존 버전을 다시 실행한다.

헬퍼는 업데이터를 시작한 뒤 HTTP 서버를 정상 종료한다. 영상 인코딩, 프레임 업로드, AE 전송 등 요청 처리 중에는 종료하지 않는다.

## 상태와 동시성

- 요청 시작/종료를 세는 작은 상태 객체를 둔다.
- 업데이트는 활성 요청 수가 0일 때만 시작한다.
- 한 번 업데이트를 예약하면 중복 업데이터를 만들지 않는다.
- `/ping` 응답에 현재 빌드 식별자와 업데이트 가능 여부를 추가하되 기존 `ok`, `ff` 필드는 유지한다.

## 배포 식별

빌드 시 소스의 `BUILD_ID`를 변경한다. 실행 파일 비교의 최종 판단은 SHA-256으로 하므로 빌드 식별자는 진단용이다. 웹이나 기존 호출자는 새 필드를 몰라도 정상 동작한다.

## 오류 처리

- R 드라이브 연결 실패: 조용히 다음 주기에 재시도
- 임시 복사 또는 해시 검증 실패: 임시 파일 삭제 후 현재 버전 유지
- 교체 실패: 백업 복원 후 기존 버전 재실행
- 새 EXE 실행 실패: 백업 복원 후 기존 버전 재실행

업데이트 실패가 CG 출력이나 AE 전송 실패로 이어지지 않도록 자동 업데이트 오류는 작업 API 응답과 분리한다.

## 검증

- 같은 파일이면 업데이트하지 않는 단위 테스트
- R 드라이브가 없을 때 현재 버전을 유지하는 단위 테스트
- 다른 파일을 감지하면 검증된 임시 파일과 업데이터를 준비하는 단위 테스트
- 활성 요청 중에는 업데이트를 미루는 단위 테스트
- 업데이터 스크립트에 대기, 백업, 교체, 복원, 무창 재실행이 포함되는 계약 테스트
- 기존 Node 전체 테스트와 WNS Python 스모크 테스트
- PyInstaller EXE 빌드 후 `/ping` 확인
- R 드라이브 배포 후 소스/EXE 해시와 재시작 확인
